## Schema, compatibility, migration and indexes

Existing `participants/{participantId}` and unique `registrations/{sessionId}~{uid}` remain the identity source. No second signup, participant row, role system or team requirement. PR5 roles are descriptive; `attendanceEligible` checks linked member identity, event and active participation, independently of `allocationEligible`. Missing participationState means active. Explicit inactive or deleted identity fails. Verified mentors and volunteers can attend without a solution team.

| Record | Contract |
| --- | --- |
| `registrations/{sessionId}~{uid}.event?` | Immutable known `{title,date:null|string}` metadata captured at registration/link/staff-role registration. Existing pointers without this field remain compatible. |
| `attendance/{sessionId}~{uid}` | One member/event record: `sessionId,uid,participantId,status:attended|removed,occurredAt,recordedAt,verifiedBy,method,revision,event`. Times are normalized UTC ISO strings from explicit occurrence or server time for a current check-in. `recordedAt` is always server request recording time, never client supplied. Corrections replace current state, increment revision and preserve the original event snapshot. |
| `attendanceAudit/{sessionId}~{uid}~{requestId}` | Private successful mutation and replay receipt: `attendanceId,sessionId,memberUid,staffUid,action,status,occurredAt,recordedAt,method,reason,evidence,revision,fingerprint,previous`. Previous contains only status/time/revision. Request IDs cannot be reused with a different actor or payload. Duplicate check-ins do not create duplicate audits. |
| `historyVisibility/{sessionId}~{uid}` | Owner selection `{uid,sessionId,visible}`. Missing means private. Applies to the history entry, including later corrections. Removal of verification changes the shared summary immediately on its next fetch. |
| `attendanceCleanup/{uid}/items/{sha256(path+kind)}` | Private deterministic retry manifest `{path,kind:subject|verifier}`. Every discovery completes before any personal search key is removed. Each item is consumed atomically with its target cleanup. |

No new composite index: queries use one equality (`uid`, `memberUid`, `staffUid`, `verifiedBy`, `sessionId`, or `attendanceId`) and sort in memory. Existing Firestore automatic single-field indexes suffice. No automatic attendance migration/backfill is permitted. Legacy registration never proves attendance. Optional `scripts/snapshot-history.ts` only captures currently known event metadata for validated existing pointers and active profiles, never invents attendance/date/identity. Dry run: `GCLOUD_PROJECT=<explicit-project> node --import tsx scripts/snapshot-history.ts`; append `--apply` only during an authorized migration window. No migration was executed in preparation. Already deleted events without known metadata remain `Event`/unknown; historical facts cannot be reconstructed from createdAt.

New registrations capture metadata transactionally in all three existing creation paths. Existing unsnapshotted pointers fall back to currently known session title/date until optional backfill. Attendance captures its own snapshot on first verification, so renaming/deleting a session does not destroy verified history. No event date is inferred from session.createdAt or registration time. Unknown dates stay unknown; actual attendance occurrence is displayed separately.

Deploy server/routes, rules and client together after cumulative validation. Direct reads and writes to new private collections are denied for every client, including staff; the server is the only writer. Existing registrations remain owner-readable with their safe event snapshot. `profiles/{uid}` keeps the exact `{name,state}` contract. Auth/users/platform role and event ownership are preserved.

## API, architecture and trust boundaries

All routes install after `server/identity.ts` verifies registered, verified, nonanonymous bearer authentication. UID and authority email derive only from verified claims. Staff authority reads event owner, private sessionAccess.adminEmails, platform users.role admin and the existing bootstrap platform admin; officialRoles/teamRoleLabels never authorize anything.

- `POST /api/identity/attendance`: `{sessionId,memberUid,requestId,action?:check-in|correct,method?:staff_check_in|manual_evidence,occurredAt?:ISO-with-timezone,evidence?,reason?,expectedRevision?,status?:attended|removed}`. Event owner/coadmin/platform admin only; even staff must ask another staff member to verify their own attendance. Target Auth account must be verified/enabled/nonanonymous, target and verifier profiles active, pointer canonical and participant linked/active in exactly this event. It creates attendance/audit in one Firestore transaction. Different concurrent check-in requests converge to one state and audit; retries return duplicate. Corrections require the current revision (stale edits 409), explicit occurrence date/evidence/reason. Old occurrence (>24 hours), closed events and events with a known date >24 hours ago require explicit occurrence and evidence. Future occurrences fail. `removed` revokes verification without discarding correction history; restoring it requires a correction. No user-supplied actor/server timestamp is accepted.
- `POST /event-attendance {sessionId}`: authorized staff for this event only receive current attendance and private audit. This is independent of the community profile/history surface.
- `POST /member-history {memberUid?}`: own UID defaults from token. Active owner sees full registered/verified distinction, revision, method, recording time and audit. Another active registered member sees only explicitly selected entries for an active profile. Response allowlists `sessionId,eventName,eventDate,registered,attendanceStatus,occurredAt`. No staff identity, evidence, audit, raw records or private admin emails enter community responses. Authority alone never grants another member full cross-event history.
- `POST /history-visibility {sessionId,visible}`: derives owner from token, checks active profile and own existing registration/attendance, writes only this owner selection. A supplied memberUid cannot change another person's visibility.

Data flow: existing registration -> staff verification transaction -> private current record + private audit -> history transaction reads profile lifecycle/owner choices -> explicit safe summary -> isolated `MemberHistory`. Staff form is `AttendanceEditor` alongside PR5 role controls in ParticipantsTab. MemberHistory appends to account/member pages and current event UI, including staff-only mentor/volunteer dashboard. PR2 professional profile/editor is preserved on final integration; append this component rather than replacing PR2 markup.

Refresh buttons/window focus reload history; no false realtime guarantee is made. A refreshed community request rechecks visibility/profile state transactionally. Previously rendered information can remain visible until refresh, as with existing profile screens. Nothing is available to signed-out/anonymous users.

## Deletion and final PR1 reconciliation

`cleanupAttendance(database,uid)` in `server/attendance-cleanup.ts` is the deterministic seam, currently called just after the durable deleting profile flag and before parent recovery keys are erased. It performs five discovery passes: subject attendance uid, subject audit memberUid, visibility uid, verifier attendance verifiedBy, verifier audit staffUid. Persist all discovered IDs before removing any UID keys. Subject attendance/audits/visibility are erased. For retained other-member attendance, null the deleted verifier UID. For its audit, null staffUid and clear free-text reason/evidence/fingerprint (which could identify the verifier). No name/email snapshots of staff are retained. Retain nonpersonal event content and other member history. New attribution from a racing correction is preserved by checking the current verifier UID before scrubbing. Manifest item and target operation share one transaction, so partial failure/retry cannot lose its work.

Attendance mutations read BOTH subject and verifier profile fences; visibility and backfill read the owner fence. Transactions serialize with profile deletion. Existing parent cleanup uses BulkWriter on this checkpoint; PR6 does not introduce an independent BulkWriter or replace parent cleanup. Before publication, merge these discovery IDs and mutations into PR1's FINAL durable cleanup manifest and mutation-generation fencing. In particular, preserve recovery IDs before registration/participant erasure, scope manifest work to the final deletion generation, and prevent a stale deletion worker touching a recreated profile generation. This is a mandatory integration gate, not claimed complete against the moving parent. Tests cover deletion/check-in/visibility races, retry after lost search keys, and verifier-deletion/correction attribution races.
