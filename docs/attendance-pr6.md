## Schema, compatibility, migration and indexes

Existing `participants/{participantId}` and unique `registrations/{sessionId}~{uid}` remain the identity source. No second signup, participant row, role system or team requirement. PR5 roles are descriptive; `attendanceEligible` checks linked member identity, event and active participation, independently of `allocationEligible`. Missing participationState means active. Explicit inactive or deleted identity fails. Verified mentors and volunteers can attend without a solution team.

| Record | Contract |
| --- | --- |
| `registrations/{sessionId}~{uid}.event?` | Immutable known `{title,date:null|string}` metadata captured at registration/link/staff-role registration. Existing pointers without this field remain compatible. |
| `attendance/{sessionId}~{uid}` | One member/event record: `sessionId,uid,participantId,status:attended|removed,occurredAt,recordedAt,verifiedBy,method,revision,event`. Times are normalized UTC ISO strings from explicit occurrence or server time for a current check-in. `recordedAt` is always server request recording time, never client supplied. Corrections replace current state, increment revision and preserve the original event snapshot. |
| `attendanceAudit/{sessionId}~{uid}~{requestId}` | Private successful mutation and replay receipt: `attendanceId,sessionId,memberUid,staffUid,action,status,occurredAt,recordedAt,method,reason,evidence,revision,fingerprint,previous`. Previous contains only status/time/revision. Request IDs cannot be reused with a different actor or payload. Duplicate check-ins do not create duplicate audits. |
| `historyVisibility/{sessionId}~{uid}` | Owner selection `{uid,sessionId,visible}`. Missing means this new history entry is absent from the community profile. Existing event rosters and official results may independently show participation. Selection shares only the safe summary and actual attendance occurrence; audits remain private. Applies to the history entry, including later corrections. Removal of verification changes the shared summary immediately on its next fetch. |
| `profileDeletionJobs/{uid}.attendancePlan` | Namespaced private `{version:1,targets:[{path,kind:subject|verifier}],completed:boolean}`. Captured under parent attempt/profile fence before identity erasure; full IDs retained through partial retries until parent completes. Coexists with `awardPlan` and parent participant/proposal recovery IDs. |

No new composite index: queries use one equality (`uid`, `memberUid`, `staffUid`, `verifiedBy`, `sessionId`, or `attendanceId`) and sort in memory. Existing Firestore automatic single-field indexes suffice. No automatic attendance migration/backfill is permitted. Legacy registration never proves attendance. Optional `scripts/snapshot-history.ts` only captures currently known event metadata for validated existing pointers and active profiles, never invents attendance/date/identity. Dry run: `GCLOUD_PROJECT=<explicit-project> node --import tsx scripts/snapshot-history.ts`; append `--apply` only during an authorized migration window. The metadata script was exercised only against synthetic emulator fixtures; no production migration was executed. Already deleted events without known metadata remain `Event`/unknown; historical facts cannot be reconstructed from createdAt.

New registrations capture metadata transactionally in all three existing creation paths. Existing unsnapshotted pointers fall back to currently known session title/date until optional backfill. Attendance captures its own snapshot on first verification, so renaming/deleting a session does not destroy verified history. No event date is inferred from session.createdAt or registration time. Unknown dates stay unknown; actual attendance occurrence is displayed separately.

Deploy server/routes, rules and client together; cumulative validation is described below. Existing registrations remain owner-readable with their safe event snapshot. `profiles/{uid}` keeps the exact `{name,state}` contract. Auth/users/platform role and event ownership are preserved.

## API, architecture and trust boundaries

All routes install after `server/identity.ts` verifies registered, verified, nonanonymous bearer authentication. UID and authority email derive only from verified claims. Staff authority reads event owner, private sessionAccess.adminEmails, platform users.role admin and the existing bootstrap platform admin; officialRoles/teamRoleLabels never authorize anything.

- `POST /api/identity/attendance`: `{sessionId,memberUid,requestId,action?:check-in|correct,method?:staff_check_in|manual_evidence,occurredAt?:ISO-with-timezone,evidence?,reason?,expectedRevision?,status?:attended|removed}`. Event owner/coadmin/platform admin only; even staff must ask another staff member to verify their own attendance. Target Auth account must be verified/enabled/nonanonymous, target and verifier profiles active, pointer canonical and participant linked/active in exactly this event. It creates attendance/audit in one Firestore transaction. Different concurrent check-in requests converge to one state and audit; retries return duplicate. Corrections require the current revision (stale edits 409), explicit occurrence date/evidence/reason. Old occurrence (>24 hours), closed events and events with a known date >24 hours ago require explicit occurrence and evidence. Future occurrences fail. `removed` revokes verification without discarding correction history; restoring it requires a correction. No user-supplied actor/server timestamp is accepted.
- `POST /event-attendance {sessionId}`: authorized staff for this event only receive current attendance and private audit. This is independent of the community profile/history surface.
- `POST /member-history {memberUid?}`: own UID defaults from token. Active owner sees full registered/verified distinction, revision, method, recording time and audit. Another active registered member sees only explicitly selected entries for an active profile. Response allowlists `sessionId,eventName,eventDate,registered,attendanceStatus,occurredAt`. No staff identity, evidence, audit, raw records or private admin emails enter community responses. Authority alone never grants another member full cross-event history.
- `POST /history-visibility {sessionId,visible}`: derives owner from token, checks active profile and own existing registration/attendance, writes only this owner selection. A supplied memberUid cannot change another person's visibility.

Data flow: existing registration -> staff verification transaction -> private current record + private audit -> history transaction reads profile lifecycle/owner choices -> explicit safe summary -> isolated `MemberHistory`. Staff form is `AttendanceEditor` alongside PR5 role controls in ParticipantsTab. MemberHistory appends to account/member pages and current event UI, including staff-only mentor/volunteer dashboard. PR2 professional profile/editor and PR4 connections are preserved in the source integration; the history component appends to their existing markup. The server-committed profile guard still controls child startup. PR5 active staff-only event UI retains resources and invitations alongside history.

Refresh buttons/window focus reload history; no false realtime guarantee is made. A refreshed community request rechecks visibility/profile state transactionally. Previously rendered information can remain visible until refresh, as with existing profile screens. Nothing is available to signed-out/anonymous users.

## Integrated PR1 deletion fence and module composition

`server/profile-cleanup.ts` exports `withProfileDeletionFence<T>(database,uid,attemptId,operation:(transaction,jobSnapshot)=>Promise<T>):Promise<T>`. Every call transactionally reads both `profileDeletionJobs/{uid}` and `profiles/{uid}`, rejects a mismatched attempt or state other than deleting, awaits the callback, renews the lease, and returns the callback result. Callback reads precede its writes; lease renewal follows all callback work. A stale worker cannot create a new plan, renew a current job, scrub a target or complete a recreated profile. `beginProfileDeletion` merge-preserves all module namespaces on takeover. Parent cleanup chunks use the helper; final parent completion also checks profile state/attempt and rejects any present attendancePlan/awardPlan whose completed flag is not true. Only the parent sets the deleted tombstone and deletes the shared job.

`cleanupAttendance(database,uid,attemptId)` runs immediately after parent begin and before parent identity erasure. `planAttendanceCleanup` uses the shared fence to capture five transactional discovery queries (subject attendance uid, audit memberUid, visibility uid, verifier attendance verifiedBy, verifier audit staffUid). It stores the full immutable namespaced `attendancePlan` before any scrub and returns saved IDs on retries, even after UID search fields vanished. It never rediscovers only after scrub. Each `applyAttendanceCleanupTarget` validates its target against the saved plan and rereads the current target inside the SAME fenced transaction. Subject records are deleted; retained other-member attendance clears only a currently matching deleted verifier; its audit clears staffUid/reason/evidence/fingerprint only while staffUid still matches. A correction introducing another verifier is preserved. IDs stay in the shared job through all partial attempts; no independent item deletion, profile tombstone, job deletion, BulkWriter or unfenced planning/mutation writes occur. A final fenced update marks attendancePlan.completed true after every target succeeds. Any failure propagates and parent cannot complete. Auth/users/event ownership remain unchanged.

The awards author adopted exact helper file from checkpoint `52eaa21b20ae0c933636085a08d0abc8d5d8827e` and agreed on `awardPlan.completed`; the modules remain isolated and coexist through job namespace merges. PR7 composition awaits both module cleanups after parent begin before writer.finish; no duplicate shared helper edits. ## Shared-content integrity follow-up

The PR6 shared cleanup queue also hardens an inherited stale-snapshot mutation path: a valid deleting generation alone cannot protect surviving peers if queued arrays/text were computed before peer edits. `writer.transform(reference, operation(currentSnapshot))` queues a conditional operation, not a replacement snapshot. Its fenced batch reads ALL shared target documents before ANY writes, evaluates each operation from those current snapshots, and retries on concurrent changes. Missing shared targets are idempotent. The generic withProfileDeletionFence signature and attendance/award completion gates are unchanged.

`server/shared-content-cleanup.ts::queueSharedContentCleanup` replaces the parent's precomputed team arrays/attribution/challenge prose writes. It filters only the deleting identities from CURRENT member lists and clears leadership/createdBy/nameSubmittedBy only while the CURRENT value matches the deleted UID or participant ID. Forming teams are canceled only while their CURRENT leader belongs to the deleted identity. Legitimate joins, leaves and newer peer names/attribution survive; concurrent A/B deletions cannot restore each other.

The private shared deletion job additionally retains `sharedContentPlan`: original proposal paths/names and challenge paths/proposal IDs/known original attribution slots. Slots are matched against the deleting member/proposal's known names, so a different surviving author is not learned as deletion attribution. The plan is captured through the attempt/profile fence before source identity erasure and reused through retry; newer prose is read at commit and only matching original attribution is anonymized. It never restores a queued old summary or blindly clears a fresh author. Parent completion alone removes this plan together with its other recovery keys.

Real `tests/shared-cleanup.test.ts` coverage pauses after queue construction, performs authorized C join/B leave, updates names/attribution/prose through actual rules, then resumes. It also covers concurrent A/B deletions, preserved new attribution before capture and across retry, missing shared targets, and stale conditional workers after actual deletion takeover/profile recreation. The suite remains sequential with all preceding slices. This follow-up is owned by PR6's shared-cleanup integration; no parent PR history is amended.
