# Reusable profile details (PR2)

PR4 integration note: historical PR2 results below describe its isolated slice. In the current stack, approved connections and selected-only contact projection are enabled as specified in [connections-pr4.md](connections-pr4.md).

## Canonical data and trust boundary

- `profiles/{uid}` remains exactly `{name, state}` for active profiles. Canonical name, uid, lifecycle, Auth, registration, event roles and platform authority retain PR1 semantics.
- `profileDetails/{uid}` is owner-only: `{professional: {avatarUrl?, bio?, title?, company?, work?, skills?, linkedin?, github?, portfolio?}, communityFields: ProfessionalField[], contacts: {contactEmail?, phone?, telegram?, whatsapp?}, connectionFields: ContactField[], whatsappUsesMobile?: boolean}`. Professional/contact values remain strings. Optional values and both selections default to empty. Professional title is free text, never an official event/team/platform role. Login email is never copied into contact email.
- `memberDetails/{uid}` contains ONLY selected, populated professional key/value pairs. No name, contacts, lifecycle or sharing configuration. Verified members can get it while the target profile is active; list/client writes remain denied. Names come from `profiles`.
- `connectionFields` is ONE global contact selection for ALL approved connections. PR4 materializes only its selected populated contact values in `connectionContacts/{uid}` atomically on validated save (also initializing existing canonical selections at mutual acceptance). Only a currently accepted connection with both profiles active can GET the contact projection; no lists or per-connection overrides. Pending requests and unrelated members cannot access it. Saved value/selection changes apply to ALL current/future approved connections, and unfriend/block revoke both directions immediately. Already copied data cannot be recalled. See the PR4 contract for transactional relation and block authorization.
- New `profilePhotos/{uid}` is `{version: UUID, bytes: Buffer}` containing one normalized raster. All direct client reads, lists and writes are denied, including owner/admin. The bytes field is exempt from indexing in `firestore.indexes.json`.

`POST /api/identity/save-profile` takes `{name, ...ProfileDetails, photoUpload?: {contentType, base64} | null}`. Identity comes only from the checked verified/non-anonymous token. Unknown keys, authority changes, invalid selections, control characters, unsafe links and bounds violations are rejected. Omit `photoUpload` to keep the current photo; null removes it; an object replaces it. The editor keeps file selection/removal and sharing as drafts until Save. The transaction replaces canonical name, private source, selected member/contact projections and photo bytes atomically. Response is `{saved: true, details: ProfileDetails}` with the authoritative photo reference; upload bytes never enter details/projection. The source photo reference is an optimistic precondition: stale, forged, cross-owner or resurrected references fail with 409 and require reload.

## Optional photo upload and storage

This MVP uses the existing named Firebase Firestore database for a deliberately small avatar, rather than adding a bucket service. Existing Firebase config names a Storage bucket, but this repository had no Storage rules or server upload/read setup. No bucket, public tokenized `downloadURL`, external image-fetching proxy or new infrastructure is required. Tradeoff: photo bytes consume Firestore storage/reads; this is bounded avatar storage, not general media storage.

JPEG, PNG and WebP uploads have a 2 MiB decoded-file limit and a 3 MiB actual JSON-body limit (including base64 overhead). Trusted `sharp` decoding verifies actual content matches the declared raster type, rejects animation/SVG/corruption and inputs over 16 million pixels, applies EXIF orientation, strips metadata and resizes within 512×512 without enlargement. Only reencoded WebP up to 256 KiB is stored. Names, original files and metadata are discarded. Authentication runs before image processing. Body-size/parse failures return accessible JSON errors; the editor also validates type/size, previews the chosen local file, supports replacement/removal and announces failures.

`professional.avatarUrl` stays a string for compatibility. New references have the exact relative form `/api/identity/photo/{uid}/{version}`. They contain no bearer or download token. `ProfilePhoto` in `src/profile-details.tsx` fetches with the signed-in Firebase bearer and renders a local object URL. Downstream photo consumers must use this component, not a raw `<img src={avatarUrl}>` for managed paths. Legacy saved HTTPS references remain readable/removable/replacable, but the editor has no URL input and the server cannot introduce new arbitrary URLs. No legacy external photo is fetched or copied by the server; its original remains controlled by its host.

Authenticated `GET /api/identity/photo/:memberId/:version` checks that both caller and target profiles are active, exact current asset version and the current canonical reference (owner) or selected member projection (other verified members with active profiles) in one transaction. Owner photos remain private unless explicitly selected. Admin role grants no private photo access. Missing/deleting/deleted caller profiles have no owner/admin exception and return 404, as do missing/unselected/deleted/stale target references; absent bearer returns 401; anonymous/unverified identities return 403. Responses, including authorization failures, use `Cache-Control: private, no-store`, `Vary: Authorization` and `X-Content-Type-Options: nosniff`. The React request uses AbortController and a cancellation fence; consent removal/unmount cannot let an older response restore the image. Object URLs are released on replacement/unmount.

Replace/remove deletes the previous bytes atomically with source/projection changes; old URLs become unavailable immediately on subsequent reads. Profile deletion adds deterministic `profilePhotos/{uid}` to PR1's existing attempt-fenced bounded cleanup transactions alongside details and projection. Deleting state hides photo reads immediately. A failed cleanup retains the durable manifest and retry path. Every mutation batch checks the current attempt; an older paused attempt cannot delete a recreated profile's fresh bytes. There is no asynchronous bucket deletion or orphan-asset job.

## Skills and existing teaming integration

Skills use a searchable multi-select combobox, dropdown, selected removable chips and an explicit custom-add option. Keyboard supports arrows/Enter, Escape and empty-query Backspace removal; combobox/listbox/options expose expanded, active-descendant, multi-select and selected state. Suggestions are a small local vocabulary, not an external service. Custom terms persist with predefined terms. The existing string contract stays compatible: canonical skills are comma-separated, trimmed, whitespace-normalized and deduplicated case-insensitively. Server and UI enforce at most 20 terms, 60 characters per term and 500 characters total. Old free-text skills remain visible/editable. Corrective chip/Backspace removals always update the draft, even when remaining legacy terms still exceed current limits; new additions and final Save enforce all bounds. Legacy terms beyond the limits can therefore be removed progressively before saving.

Professional details and skills do **not** feed the current team-matching algorithms. PR2 currently displays its selected projection on member profile pages via `MemberDetails` (`src/identity.tsx`, `src/profile-details.tsx`). Existing participant registration writes event name/adjective/design-thinking proficiency and identity (`server/identity.ts`, `/register`). AI discovery serialization in `src/pages/admin/TeamsTab.tsx` maps `id`, `name`, `designThinkingProficiency`, `adjective`, and focus-area interests; AI solution serialization maps `id`, `name`, proficiency, challenge and primary/secondary archetypes. Neither reads `profileDetails`, `memberDetails`, professional title or skills. Deterministic assignment also uses event proficiency/archetypes. `server.ts` forwards the existing prompt; it does not enrich it from profiles. This change deliberately preserves those matching behaviors. Broader team-card display integration is a separate downstream contract consumer coordinated by the root thread.

`registrationDefaults` stays canonical for event adjective/design-thinking proficiency; workshop answers/archetypes remain event-specific. No extra signup, name source or professional-to-event data copying is introduced.

## Migration, deployment and rollback

Additive server-only photo collection requires no backfill. Old name-only profiles remain compatible; missing optional source means empty/private. Existing HTTPS photo references require no data migration and cannot be newly forged through save. Never infer private contacts from historical participants.

Deploy restrictive Firestore rules, bytes-index exemption and trusted server together before exposing the editor. Normal runtime keeps PR1's named database; emulator config stays synthetic default. Server runtime needs Node 24 and the lockfile's `sharp` native package (normal `npm ci` on a supported deployment platform). Existing Admin SDK database credentials suffice; no Storage rules, bucket IAM, Storage emulator or additional environment variables are needed. Do not substitute a fake upload if the server is absent. Rollback UI first; retain restrictive rules and cleanup of `profilePhotos`, `profileDetails` and `memberDetails` until data retirement. Production deployment is outside this implementation checkpoint.

## Contact revision and downstream seam

The optional contact allowlist is `contactEmail`, `phone` (mobile), `telegram`, `whatsapp`. All values remain strings. `whatsappUsesMobile?: boolean` is additive **owner-private** source metadata; missing means false, Save writes an explicit boolean. Only an explicit checked choice derives canonical WhatsApp from mobile on every Save. A missing/invalid linked mobile is correctable by entering an international number or unchecking the choice. Unchecking retains the current number as an independent editable draft. Neither mode nor matching numbers changes either sharing selection. All edits, selections and mode remain drafts until Save. The owner editor uses separate native country-code selectors and national-number inputs for Mobile and WhatsApp. No country is selected for a new number; owners explicitly choose it or paste a full +international number. UI-only drafts use pinned `libphonenumber-js` 1.13.16 with its complete supported-country/calling-code metadata and strict national parsing (GB trunk zero removed, Italian significant zero retained). Country names come from `Intl.DisplayNames`, never locale-based country inference. [Official library documentation](https://github.com/catamphetamine/libphonenumber-js#readme) documents `getCountries`, `getCountryCallingCode`, `parsePhoneNumberFromString` and strict `extract: false`. The dependency adds no network requests, phone lookup or ownership verification. Country selection preserves national digits; international paste overrides a selected prefix without doubling it. International dialing prefixes that parse to a different calling code are rejected with instructions to paste a full +number, rather than re-prefixing the foreign number. An untouched unrecognized legacy +code stays compatible; explicitly choosing a country requires correcting that value before Save. Loaded/pasted international digits bypass national-prefix rewriting until the owner edits them. A country-only empty draft remains optional. Linked WhatsApp mirrors and disables both controls; unchecking retains the mirrored number as its editable separate draft. Sharing flags remain independent. Canonical contacts remain E.164 strings under the existing API validation; no schema, rules, migration or persisted country metadata changes. Existing E.164 values hydrate losslessly, including non-geographic and unrecognized legacy calling codes; malformed legacy text remains correctable/clearable. Edited national digits under a neutral shared calling code require an explicit country choice, or a new full +international paste; Save rejects without writes until corrected. Non-geographic calling codes have a distinct label and require a full +international paste when edited. Shared calling codes (including +1 and +44) reload with a neutral “shared calling code” option rather than a guessed country. A chosen country is intentionally UI-only and may therefore not survive reload. Existing nonallocated but structurally accepted numbers remain compatible; the parser does not assert numbering-plan validity. Sharing WhatsApp reveals its registered number ([official click-to-chat format](https://faq.whatsapp.com/5913398998672934)).

Telegram accepts plain username, @username, `t.me/username` or exact HTTPS profile link, stored as @username with an owner-only link preview. Safe single-path parsing rejects credentials, other hosts, extra paths, queries, fragments and encoded routes. The character allowlist includes short collectible names rather than imposing the basic username creation minimum; values remain self-reported ([Telegram FAQ](https://telegram.org/faq#q-what-can-i-use-as-my-username), [public username links](https://core.telegram.org/api/links#public-username-links)). Legacy malformed Telegram values remain visible and editable; the editor asks to correct or clear them before Save and preserves unrelated drafts on failure. Standard native email/tel autocomplete supports user-chosen autofill. No clipboard/contacts read or permission, provider login, app detection or bot is introduced. [Contact Picker](https://developer.mozilla.org/en-US/docs/Web/API/Contact_Picker_API) has limited browser support and standard contact data rather than Telegram usernames. [Official Telegram Login](https://core.telegram.org/bots/telegram-login) requires a bot, registered allowed URLs and credentials; that is separate future scope.

Signal is retired: old source payload keys and sharing entries are tolerated as input solely to drop them, including malformed retired values. Save atomically replaces the source without Signal. The editor never displays or selects it, and `contactFields` never permits its future projection. No production data is changed here. Before PR4 enables contact reads, deploy fail-closed projection rules and a coordinated migration/backfill removing Signal from stale `connectionContacts` documents and retiring source values; filtering only new saves cannot repair previously stored projections. PR2 keeps `connectionContacts` deny-all. Downstream must project only the current allowlist, never spread source contacts, expose `whatsappUsesMobile`, infer sharing from linked mode, or couple phone/WhatsApp consent. Preserve these restrictions on rollback until legacy data retirement is complete.
